# Let's Connect

A PWA that gives couples curated questions to discuss, one full-screen card at a time.
Pick a depth, talk about the card, tap **Completed** or **Skip**, and never see the same
question twice.

**No answers are ever recorded.** The database stores only *that* a card was dealt with,
which is all that is needed to stop it coming round again. That is a deliberate design
constraint, not an unfinished feature — the whole point is that the conversation stays
between the two people having it.

---

## The stack

Deliberately boring and dependency-light. **No build step, no bundler, no TypeScript.**

| Layer | Choice |
|---|---|
| Server | Node + Express, single `server.js` |
| Front end | Vanilla-JS SPA (`public/app.js`), no framework |
| Database | MariaDB via `mysql2/promise`, one shared pool (`db.js`) |
| Auth | `express-session` + `bcryptjs`, sessions stored in MySQL |
| Email | `nodemailer`, configured in the admin UI rather than `.env` |
| PWA | `manifest.webmanifest` + `sw.js`, icons generated by a script |

Six runtime dependencies in total.

## The seven levels

Ordered by depth, not by topic. The intent is that you choose by how much energy and
honesty you both have tonight.

| Level | Depth | What it is |
|---|---|---|
| **Icebreakers** | 1 | Light, playful, nothing at stake |
| **Everyday Us** | 2 | Chores, money, time, phones — where the friction actually lives |
| **Our Story** | 3 | Memories and beginnings |
| **Heart to Heart** | 4 | Needs, appreciation, the things easier felt than said |
| **Dreams & Plans** | 4 | The future, practically as well as hopefully |
| **Deep Waters** | 5 | Fear, shame, grief, the things never said |
| **Just Between Us** | 5 | Romance, desire, closeness |

**35 questions each, 245 in total.** All of it lives in
[`data/catalogue.js`](data/catalogue.js), which carries its own editing rules at the top.

### Skip vs Completed

- **Completed** retires the question permanently.
- **Skip** means *"not tonight"*. The question is held back for `skip_cooloff_days`
  (default 14) and then becomes eligible again.

There is one guard worth knowing about: **if the cool-off is the only thing standing
between a couple and an empty deck, the skipped questions are released early.** A deck
must never dead-end while unanswered cards sit waiting on a timer. The levels list counts
`ready` (what the deck would actually serve) rather than `available` for exactly this
reason — counting `available` showed "0 ready" on decks that had cards waiting.

## Pairing

Each person has their own login. One creates the couple and gets a six-character invite
code; the other redeems it. Progress belongs to the **couple**, not the person — whoever
taps, you both stop seeing that card.

- Invite codes avoid `0 O 1 I 5 S` so they survive being read aloud or texted.
- A couple with a single member is valid — you can start before your partner joins.
- Each couple gets a `shuffle_seed`, so question order is stable and identical for both
  partners but different for every couple.
- **Leave couple** exists so a mis-typed code is not a permanent dead-end. Progress stays
  with the couple; if the last member leaves, the couple is marked `dissolved`, not
  deleted.

## Local development

Needs Node 18+ and a local MariaDB.

```bash
npm install
```

Copy `.env.example` to `.env` and fill in your local database credentials. Leave
`NODE_ENV` **unset** locally — that is what keeps the login cookie non-secure so
`http://localhost` works.

```bash
npm run init-db     # creates the database and applies schema.sql
npm run migrate     # runs migrations, seeds the 245 questions
npm start           # http://localhost:3000
```

The first account registered becomes the admin.

| Script | What it does |
|---|---|
| `npm start` | Runs the server |
| `npm run init-db` | Applies `schema.sql` (non-destructive, `IF NOT EXISTS` throughout) |
| `npm run migrate` | Runs every migration in order, then checks `schema.sql` for drift |
| `npm run check-schema` | Reports drift between `schema.sql` and the live database |
| `npm run check-schema -- --emit` | Prints the DDL to close the gap |
| `npm run make-icons` | Regenerates the PWA icons |

## Password reset

Self-serve from the sign-in screen, and admin-initiated from **Admin → People**.

- Only a **SHA-256 hash** of the token is stored, never the token. A database dump does not
  hand anybody a working reset link — a reset token *is* a password for the next hour.
- Tokens are **single-use** and expire after **60 minutes**. Requesting a new link
  immediately consumes any outstanding one.
- `POST /api/auth/forgot` **always answers identically**, whether or not the address has an
  account, and whether or not the email actually sent. Anything else turns it into a way of
  testing who has an account. Send failures are logged server-side instead.
- Completing a reset **deletes every session for that account**. If the reset happened
  because somebody else was in the account, leaving their session alive would change the
  lock with the intruder still inside. This is what `sessions.user_id` is for — matching on
  the JSON blob could not tell user 5 from user 50.
- The admin flow returns the link as well as emailing it, so it works before SMTP is set up.
  An admin can already promote themselves and read everything, so the link grants no
  privilege they did not have — and it beats the alternative, where an admin types a
  password *for* someone and then knows it.

Email is configured in **Admin → Settings**, stored in the `settings` table so it survives
redeploys with no server file editing. The SMTP password is **AES-256-GCM encrypted at
rest** under `SECRET_KEY` (falling back to `SESSION_SECRET`) and is never returned to the
browser — the API exposes only whether one is stored and whether it can still be read.

If the key changes underneath it, decryption **fails soft**: the settings page still loads,
reports the password as unreadable, and sending refuses with a message telling you to
retype it. It does not throw, because an exception there would take down every page that
reads settings.

## The master admin

A **separate app at `/admin/`**, with its own sign-in. Couples never see a door to it, and
their browser never downloads a line of its code.

It is a real static directory (`public/admin/`), not a route. With Plesk's document root at
`public/`, nginx serves it directly — a `/admin` *route* would depend on nginx falling
through to Passenger, which is one more thing to be wrong on deploy day.

Access is `users.is_owner`. The first account registered on a fresh install becomes the
owner automatically. The whole `/api/owner` namespace is gated in one place, so a new owner
endpoint is closed by default and you opt in by where you put it.

| Tab | What it does |
|---|---|
| **Overview** | Counts, per-group totals, newest accounts, outstanding reports, email status |
| **Groups** | Create, rename, recolour, set depth, reorder, hide, delete |
| **Questions** | Every question: search, filter, edit wording, move group, hide, delete |
| **Import** | Upload .xlsx/.xls/.csv, export everything, download a blank template |
| **Insights** | Skip rate per question and per group — the content quality signal |
| **Reports** | What couples have flagged, with their own words, and what to do about it |
| **People** | Search, make/remove owner, deactivate, issue a reset link |
| **Couples** | Every couple with members, code, progress and last activity |
| **Audit** | Everything done in here, newest first |
| **Settings** | Branding, cool-off, deck size, app URL, SMTP |

### Spreadsheet import

Columns are `group`, `question` and an optional `ref`. Headings are matched forgivingly —
`Level`/`Category`/`Deck` all mean `group`, `Text`/`Prompt` mean `question` — because
rejecting a good spreadsheet over a capital letter helps nobody.

**Every upload is a dry run first.** You see how many rows are new, how many update an
existing question, how many are unchanged, and every row that cannot be used with its row
number and the reason. Nothing is written until you confirm. A 300-row file is exactly the
sort of thing you do not want to find out about afterwards.

- Leave `ref` blank for new questions. Rows with no ref are matched on exact text within
  the group, so **re-uploading the same file does not duplicate anything**.
- Paste a `ref` from an export and that question is **updated in place**, keeping its id and
  therefore every couple's record of having discussed it.
- **Export is your content backup.** Content now lives only in the database, which is not in
  git — see below.

### Where content lives changed in v1.2.0

Until v1.2.0, `data/catalogue.js` was the source of truth and the seeder rewrote every
question on every deploy. Now the **database is authoritative** and the seeder is a
**first-run seed only**: on a database that already has groups and questions it does
nothing at all and says so.

That reversal was necessary — with the admin able to edit content, the old behaviour would
have rewritten every edit and switched off every addition on the next deploy. The
consequences to know:

- Editing `data/catalogue.js` after first run has **no effect** on an existing install.
  Use the import.
- Content is **not in git**. Export to Excel periodically; that is the backup.
- `questions.source` (`catalogue` / `admin` / `import`) is now provenance rather than
  ownership — useful for working out where a bad question came from.
- `admin_hidden` remains separate from `is_active` so hiding is always the owner's call.

### Two guards on People, each scoped so it actually fires

- **You cannot deactivate yourself.** No legitimate use — it signs you out on the spot.
- **You cannot remove the last active owner.** This is what makes *stepping down* safe:
  handing over and demoting yourself is a real thing, allowed exactly when somebody else
  holds the keys.

An earlier version blocked all self-demotion, which read as safer and was worse: it made
the last-owner check **unreachable** — the caller is always an active owner, so "another
owner exists" was true whenever the target was someone else — leaving the real lockout case
guarded by a rule that could never fire.

### Deleting content asks for more than a tap

- A **group with questions in it** cannot be deleted at all. Deleting would cascade the
  questions away and take every couple's record of discussing them with it — a much bigger
  consequence than "remove this heading". Empty it, or hide it.
- A **question somebody has answered** needs explicit confirmation, and the dialog says how
  many couples are affected and points out that hiding does the same job without destroying
  the record.

## Question quality

The app stores no answers, so there are exactly two signals about whether the content is any
good, and the admin area is built around both.

**Skip rate** (Insights). A question couples keep passing over is usually badly worded, too
close to another one, or lands harder than its group implies. Only questions answered at
least *N* times are ranked — sorting purely by percentage would put every 1-of-1 skip at the
top and bury the question forty couples have quietly avoided.

**Reports** (Reports). A "Report this question" option in the deck menu lets a couple say
*why*, in their own words. One report per couple per question — a second one from the other
partner updates the first rather than stacking. Resolving a report can hide the question in
the same action, since that is the usual response.

## Privacy: export and deletion

Both live in the couple app under **Account → Your data**.

- **Download my data** returns everything the app holds as JSON, including the *text* of
  each question alongside the decision. An export listing bare question ids would be
  technically complete and useless to the person reading it, which is not what portability
  means.
- **Delete my account** is irreversible, needs a typed confirmation *and* the account
  password. The password matters most: somebody who walked off leaving their phone unlocked
  should not be one tap from destroying the account.

Shared progress belongs to the **couple**, not the person, so deletion deliberately leaves
it behind — erasing it would silently delete the partner's history too, and that is somebody
else's data. The dialog says so. Once the last member goes, the couple is marked dissolved
and nothing identifies anyone.

The audit log keeps the actor's **email as recorded at the time**, so history survives the
account being deleted. A foreign key alone would blank the actor on every historic entry at
exactly the moment you most want to know who did what.

## Migrations

Every schema change is an idempotent script in `scripts/migrate-*.js`, registered in
**three** places:

1. the `MIGRATIONS` array in `scripts/migrate-all.js`, in dependency order
2. a `"migrate-<name>"` entry in `package.json`
3. the column mirrored by hand into `schema.sql`

Two guards exist, and they catch different failures:

- **The registry guard** refuses to touch the database if any `migrate-*.js` on disk is
  unregistered, or any registered name is missing. It **fails**, before connecting —
  because a migration that exists but never runs on production is how a live view goes
  silently empty.
- **The drift checker** catches step 3, which nothing else enforces. `schema.sql` is not
  applied by `migrate`, so nothing forces the two to agree. It runs after every migrate
  and only **warns**: a migration that did not run makes the app wrong *now*; `schema.sql`
  lagging only makes the *next fresh install* wrong.

The question catalogue is itself a registered migration, so **new questions ship with a
`migrate` and nothing else**. It matches on the stable `ref` key, updates text in place,
and deactivates removed entries rather than deleting them — so a couple's progress
survives any content edit.

## The PWA

Installable, works offline, portrait, standalone.

The service worker is **network-first, deliberately** — including for the app shell. The
usual cache-first advice is wrong here: a cache-first shell means a deploy is invisible
until the cache happens to expire, which is the same failure a plain browser cache
produces except a service worker makes it far stickier and much harder to clear from a
phone. Always try the network, fall back to the cache when offline.

- `/api/*` is **never** cached.
- `app.js` / `styles.css` are requested with a `?v=<timestamp>` buster; the SW strips the
  query before using the URL as a cache key, or the cache would grow without bound and
  never serve a hit.
- There is deliberately **no version constant in `sw.js`** — the cache is a fallback that
  is overwritten on every successful fetch, so there is no third place to remember to bump.

Icons are generated by `scripts/make-icons.js`, which writes real PNG bytes using only
`zlib` from Node's standard library. A native image dependency is exactly the sort of
thing that breaks an `npm install` on shared hosting.

## Deploying to Plesk

Same shape as the other Node apps on this host.

### Routine deploy

```
1. Local:  git commit + git push origin main
2. Plesk → <subdomain> → Git → Pull
3. Plesk → Node.js → Run script → migrate     ← whenever the catalogue or schema changed
4. Plesk → Node.js → Restart App
5. Browser: Ctrl+F5
```

In Plesk's "Run script" box the argument is just `migrate` — Plesk prepends `npm run`
itself.

### First-time setup

1. Create the subdomain; enable Let's Encrypt SSL + forced HTTPS.
2. **Git** extension → add the repo via the **SSH** remote, and paste Plesk's generated
   public key into GitHub → Settings → **Deploy keys** (read-only is enough). Pull.
3. **Databases** → create the database and user.
4. **Node.js** → Application Root = repo root, Startup File = `server.js`, Application
   Mode = **production**. Run **NPM install**.
5. **Hosting Settings** → Document Root = **`<subdomain>/public`**, not the repo root.
   Delete Plesk's placeholder `index.html`.
6. Hand-create `.env` in the application root from `.env.example`. **No `PORT` line.**
   Generate two *different* random strings for `SESSION_SECRET` and `SECRET_KEY`, and set
   both now — setting `SECRET_KEY` on day one is what lets `SESSION_SECRET` be rotated
   later without breaking anything encrypted at rest.
7. **Node.js → Run script → `init-db`**, then **`migrate`**.
8. **Restart App**, then register the first account (it becomes the admin).

### The three that cost time on every Plesk app

- **Document Root must be `public/`.** With it set to the repo root, Passenger serves the
  folder as plain static files and you get a bare **403**. This setting can also silently
  revert after a Passenger restart — if the live site 403s or routes wrongly after a
  deploy, check the docroot *before* reading any application code, and if re-applying it
  is not enough, **Disable → Enable** Node.js rather than just restarting.
- **Never set `PORT` in production.** Passenger assigns it.
- **`.env` is gitignored and never deployed.** It is hand-created once on the server and
  survives every pull.

`trust proxy` + secure cookies are already handled under `NODE_ENV=production` — without
both, the login POST succeeds behind Plesk's HTTPS proxy and then every subsequent request
comes back unauthenticated.

## Versioning

Since v1.2.0 there are **three** stamps, not two, and they must all match:

- `package.json` → `"version"` (the server)
- `public/app.js` → `APP_VERSION` (the couple app)
- `public/admin/admin.js` → `APP_VERSION` (the admin app)

```bash
grep -n "1\.2\.0" package.json public/app.js public/admin/admin.js
```

That must return **three** lines. A mismatch shows as `vX ⚠ server vY` in the footer of
whichever app is stale — a real bug, not a cosmetic one, because the served script is
reporting a version it is not.

⚠️ **Do not edit these files with PowerShell.** In Windows PowerShell 5.1, `Get-Content`
reads as ANSI rather than UTF-8, so a `Get-Content | … | Set-Content` round trip
double-encodes every non-ASCII character in the file — `→` becomes `â†’`, `❤` becomes `â¤` —
and adds a BOM. It happened here and corrupted both `server.js` and `public/app.js`. Use an
editor, or `node -e` with explicit `utf8` reads and writes.

Default to **patch**. Reserve **minor** for a genuinely new capability, a schema change,
or a release that adds questions.

## Not built yet

Worth being explicit about, so nobody goes looking:

- **One couple per person.** Enforced by `UNIQUE(user_id)` on `couple_members`. Leaving is
  the way out.
- **Content is not in git.** Since the database became authoritative, the only backup of
  your groups and questions is the Excel export. Take one before anything risky.
- **No privacy policy or terms pages.** Export and deletion are built; the documents that
  usually accompany them are not, and a consumer app holding personal data is expected to
  have both.
- **The installed PWA icon is not brandable.** Name, tagline, colour and the logo character
  are; the home-screen PNG is generated by `npm run make-icons` and needs a deploy.
- **No email verification on sign-up.** Anyone can register with any address. The reset
  flow is safe regardless (it emails the address on the account), but nothing proves the
  address is yours at registration.
- **Login throttling is per worker.** It is in-memory, and Passenger runs several workers,
  so it slows a brute-force attempt rather than stopping it dead. bcrypt is the real
  protection. Moving the counter into the database would fix it properly.
- **No admin audit log.** Promotions, deactivations and issued reset links are not
  recorded anywhere.
- **Admins cannot delete a couple or a person**, only deactivate an account. Deletion
  would cascade progress away, and nothing has asked for it yet.
