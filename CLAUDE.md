## 1. Working with Grant: standing rules

- **Instructions click-by-click.** Number every step and name the exact Plesk screen and button, for example **Websites & Domains** → **connect.launchyourlife.co.za** → **Git** → **Pull Updates**.
- **Every commit message starts with `vX.Y.Z - `**, including fixups, docs and housekeeping. Grant reads the log in GitHub and in the Plesk Git panel, where only about 60 characters show. A commit that does not bump carries the version it belongs to.
  - The rest of the message is prose: why, and what was learned. Write it to a scratchpad file and commit with `git commit -F`.
  - **Never rewrite a pushed commit** to fix its name. A force-push makes Plesk's pulled copy diverge from GitHub, which can mean removing and re-adding the repository in Plesk **Git**.
- **Three version stamps must match:** `package.json` `"version"`, `APP_VERSION` in `public/app.js`, and `APP_VERSION` in `public/admin/admin.js`. `grep -n "X.Y.Z" package.json public/app.js public/admin/admin.js` must return three lines. A mismatch shows a "server vY" warning in that app's footer.
  - PATCH by default. MINOR for a genuinely new capability, a schema change, or a release that adds questions.
- **Never edit source files with PowerShell** `Get-Content`/`Set-Content`. Windows PowerShell 5.1 reads them as ANSI, silently double-encodes every non-ASCII character (`→` becomes `â†’`) and adds a BOM. It corrupted `server.js` and `public/app.js` on 2026-08-15. In `.env` the BOM lands inside the first key name. Use the Edit/Write tools, or `node` with explicit `'utf8'` reads and writes.
- **Never retype a regex through a shell.** Heredocs and one-liners can eat backslashes and still leave a valid regex: `\s` became `s`, and `/api/register` refused every email containing an "s" for two releases (fixed v1.20.2).
  - Copy a correct regex programmatically. After a bulk edit, grep for `[^s@]`, `d{`, `w+` and similar stripped shapes.
  - Test the input a guard should refuse, not only one it should accept.
- **`Research Data/` is Grant's.** Don't read, summarise, mine or build from it unless Grant asks. `npm run build-corpus` reads a file in it, so run that only when asked.
- **Decisions Grant made. Don't quietly revisit them:**
  - **No answers are ever stored**, only that a card was dealt with. That is the point of the app, not a missing feature.
  - **Skip is reversible**: "not tonight", not "never". It returns after the cool-off (`skip_cooloff_days`, default 14). Grant rejected a permanent Skip.
  - **Pairing by a shared code**, chosen over a shared login or solo-first. Progress belongs to the couple.
  - **Sessions last 60 days of inactivity**, and owner sessions share the same cookie, so the admin gets 60 days too. Grant said leave it (v1.24.1). Shortening the cookie would sign every couple out.
- **Port 3200 is this app's.** Port 3000 belongs to the AppFirm CRM. Never default any new app to 3000.

## 2. Stack and files

- Express `server.js` (one file, about 5,400 lines) + `db.js` (one `mysql2` pool, limit 5), MariaDB. Vanilla JS, no framework, no build step. `engines` says Node 18+.
- **Couple app:** `public/index.html`, `public/app.js`, `public/styles.css`, `public/sw.js`, `public/icons/`. The manifest is generated by `server.js` at `/manifest.webmanifest`.
- **Owner admin:** a separate static app at `/admin/` (`public/admin/index.html`, `admin.js`, `admin.css`) with its own sign-in. Tabs: Overview, Topics & depths, Questions, Develop, Sequences, Import, Insights, Reports, People, Codes, Audit, Email, Settings. The whole `/api/owner` namespace is gated in one place.
- **How couples get in:** one access code per couple, typed on the welcome screen (`/api/access/redeem`). Codes are issued in **Admin → Codes**, requested on the register page (`/api/register`), or minted by the launchyourlife.co.za shop calling `POST /api/shop/codes` with an `x-shop-key` header (returns 501 until a shop key is set).
- **Owner accounts:** email + password (bcryptjs). The first account on an empty database becomes the owner; `/admin/` shows a setup screen while `users` is empty.
- **Sessions:** express-session with a custom MySQL store. The `sessions` table is created by the app at boot, not by `schema.sql`.
- **Settings live in the `settings` table, not `.env`:** branding, brand images (stored base64, not on disk), cool-off, deck size, `app_url`, SMTP (**Admin → Email**), Anthropic key and model (**Admin → Develop**), and the shop key (**Admin → Settings**). The SMTP password and Anthropic key are AES-256-GCM encrypted under `SECRET_KEY`. No secret is ever sent to the browser. `.env` `ANTHROPIC_API_KEY` is only a fallback.
- **AI:** **Develop** drafts questions through a server-side proxy. Drafts land in `question_drafts`, are checked by `lib/question-rules.js`, and are never served until approved.
- **Content:** the **database is the source of truth** for questions. `data/corpus.json` is a first-run seed only (`migrate-seed-corpus` does nothing once questions exist). `npm run seed-corpus -- --replace` deletes all content and every couple's progress: never on live. Content is not in git; **Admin → Import → Export everything to Excel** is its backup.
- **No uploads folder.** multer uses memory storage and images go into the database.
- `schema.sql` = non-destructive fresh-install DDL (`IF NOT EXISTS`), NOT applied by migrate. npm scripts: `init-db`, `migrate`, `check-schema` (`-- --emit` prints the fix), one `migrate-...` per migration, `build-corpus`, `seed-corpus`, `rewrite-questions` (dry run unless `-- --apply`), `make-icons`, `kill-stray`.
- Gitignored: `.env`, `node_modules/`, `.claude/`, `scratch/`, `*.log`, and curl cookie jars and header dumps (`*.cookies`, `lc*.txt`, `headers.txt`). One cookie jar (`lc2.txt`, a dev-only session) was committed in v1.14.0 and removed the same day.

## 3. Dev environment and testing

- Local MariaDB 11.4 (Windows service, port 3306). Database **`lets_connect`**, user **`root`**. The password is in `.env` only. Laptop runs Node 24.
- **Launch** with preview config **`lets-connect`** (`.claude/launch.json`, `npm start`, port 3200), or `npm start` and open http://localhost:3200 (couple app) and http://localhost:3200/admin/ (owner admin).
- Leave `NODE_ENV` **unset** locally. That keeps the login cookie non-secure so http://localhost works.

- **Fresh dev database:** copy `.env.example` to `.env`, then `npm run init-db`, then `npm run migrate` (it also seeds the starter questions). Then create the owner account at `/admin/`.
- **Test logins:** the dev owner account is in the local `users` table (`is_owner = 1`). Its password is not recorded in memory or in this file: ask Grant, or look in the password manager. Never write it here. For a test couple, issue a code in **Admin → Codes**.

## 4. Deploy (Plesk)

- **Live:** https://connect.launchyourlife.co.za on the NOIZ Plesk host, subscription **launchyourlife.co.za**. The main domain's `httpdocs` holds a live WordPress site.
- **Pipeline:** `git push origin main` → private GitHub repo `grantjoyce/LetsConnect` → Plesk **Git** pulls over a read-only SSH deploy key → **Restart App**. Live changes only when Grant pulls. The laptop pushes through the SSH alias `github-letsconnect` (key `~/.ssh/letsconnect_deploy`).
- **Check live yourself; never act on it.** `curl -s https://connect.launchyourlife.co.za/api/health` gives the server version (read at boot, so it changes on Restart App). `curl -s https://connect.launchyourlife.co.za/app.js | grep -m1 "const APP_VERSION"` changes on Pull Updates alone.

**Steps to give Grant for every release** (say which optional steps apply):
1. Log in to Plesk: noiz.co.za client area → **Manage** → **Log in to Plesk**.
2. **Websites & Domains** → **connect.launchyourlife.co.za** → **Git** → **Pull Updates**.
3. Only for a new npm dependency: open **Node.js**, click **NPM install**.
4. Only for a migration or new questions: on **Node.js** click **Run script**, type `run migrate`. If Plesk answers "Unknown command", type `migrate` instead (the README says plain `migrate`; the CRM on the same server needs `run migrate`).
5. On **Node.js** click **Restart App**.
6. Reload the app (Ctrl+F5).

**Run script box:**
- **Never start the server from it** (`start`, `dev`, anything long-running). It leaves an orphan `node server.js` holding the port, and SSH is Forbidden on this plan, so nobody can kill it. To prove Node, `.env` and the database work, run a script that exits: `init-db` or `migrate`.
- If an orphan exists anyway: Run script → `run kill-stray`.
- It only offers npm and yarn. There is no `npx`.

**Plesk configuration.** Three settings must all point at the subdomain's own folder:
- **Git** → repository settings → **Server path**: `/connect.launchyourlife.co.za`. It defaults wrong to `/httpdocs/public`.
- **Hosting Settings** → **Document root**: `connect.launchyourlife.co.za/public`. The repo root gives a bare 403. It can revert after a Passenger restart: re-apply it, then **Node.js** → **Disable** → **Enable**.
- **Node.js** → Application Root `/connect.launchyourlife.co.za`, Startup File `server.js`, Application Mode `production`.
- **Secrets:** a hand-made `.env` in the application root holding `DB_HOST=localhost`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`, `SESSION_SECRET`, `SECRET_KEY` and `NODE_ENV=production`, and **no `PORT` line** (Passenger assigns it). Without `NODE_ENV=production`, logins silently fail behind Plesk's HTTPS proxy.

**Never deploy into `httpdocs`.** The first deploy (2026-08-16) went there, on top of WordPress. WordPress's `.htaccess` sent every `/api` request to `index.php`: pages loaded, every API call failed, Apache logged `AH00124` redirect loops, and Passenger logged nothing. It cost a full session. When "it works locally but 404s live", look for a stray `.htaccess` in the APPLICATION ROOT, not just `public/`.

**Fresh install order:** files in place first, Node.js enabled last. Delete Plesk's placeholder `index.html`. Run script `run init-db`, then `run migrate`, then **Restart App**, then create the owner account at `/admin/`.

**Migrations:**
- Every schema change is an idempotent `scripts/migrate-*.js`, registered in three places: the `MIGRATIONS` array in `scripts/migrate-all.js` (dependency order), a `migrate-<name>` script in `package.json`, and the columns mirrored by hand into `schema.sql`.
- The registry guard refuses to run if any file is unregistered or missing. The drift checker runs after every migrate and only warns.
- Order is always pull → migrate → restart. Re-running is safe.
- There are no restore-point tags yet. Before a risky deploy, tag the live commit and push the tag.

## 5. Conventions and gotchas

- **Service worker is network-first on purpose**, app shell included, so a deploy shows on the next load. `/api/*` is never cached. `app.js`/`styles.css` load with `?v=<timestamp>` and the SW strips the query for its cache key. There is no version constant in `sw.js`.
- **No native image modules.** `npm run make-icons` writes PNGs using only `zlib`. The installed app icon comes from the uploaded favicon (v1.14.3).
- **Owner password reset does not work today.** Reset links (Admin → People → **Reset link**, or the forgot route) point at `/?reset=<token>`, but neither app reads that address since the code-only welcome screen replaced couple logins, and the admin sign-in has no "Forgot password" link. There is no `reset-password` script. See `RECOVERY.md` Scenario E.
- Reset tokens are stored only as a SHA-256 hash, single-use, 60 minutes. `/api/auth/forgot` answers the same whether or not the account exists.
- **People guards:** you cannot deactivate yourself, and you cannot remove the last active owner.
- **Deleting content:** a topic with questions in it cannot be deleted. A question couples have answered needs confirmation; hiding does the same job without destroying their record.
- **Import is a dry run first.** Rows with a `ref` from an export update in place, keeping every couple's record; rows without one match on exact text, so re-uploading a file does not duplicate.
- **Login throttling is in memory, per Passenger worker.** It slows brute force; bcrypt is the real protection.
- The audit log keeps the actor's email as it was, so history survives an account being deleted.

## 6. Backup and recovery

The launchyourlife.co.za subscription has **no Plesk backup schedule**. The live database (couples, codes, buyer emails and phone numbers, owner accounts, every question and every setting) relies on NOIZ's own server backups, and a restore means asking NOIZ support. Grant decided not to change this. So the by-hand copies matter: **Admin → Import → Export everything to Excel** before risky deploys, and Plesk **Databases** → **Export Dump** when you want everything. On the laptop, this folder and the dev database `lets_connect` are in the nightly encrypted restic backup (`ClaudeCode\nightly-backup\README.md`), and Claude's memory is in the private `grantjoyce/dotclaude` repo. Step-by-step recovery for every scenario is in **`RECOVERY.md`**.
