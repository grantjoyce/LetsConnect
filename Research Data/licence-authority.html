Launch platform · architecture note

One authority decides who has paid. Everything else asks.

How the shop and its subdomain apps should share licensing — and the one thing in Let's Connect that has to change before you sell a subscription.

Start from what is actually built

Today

Let's Connect issues its own codes. The shop calls POST /api/shop/codes with a shared key, the app mints a code against two names, and returns it once. That is a clean design and it works — for one app.

The gap

There is no licence expiry anywhere in the codebase. Every match for "expire" is a login session or a password reset. A code is active or suspended, and that is the whole model.

That is a perpetual licence. You are describing subscriptions. Nothing currently stops a code working forever, and nothing tells the app that a card payment failed in March.

The good news is bigger than the gap. The app re-reads the licence from the database on every single request rather than trusting the session cookie, so revoking access takes effect on the next tap. That was built so a refund could kill a code immediately. It is exactly the hook a central authority needs — it is simply reading a local row today instead of asking the shop.

The shape

Where licences live

With one app, it does not matter much who owns the licence. With many, it decides everything. The moment a second app exists, the question "has this person paid, and are they still paying?" must have exactly one answer, in one place.

The shop owns customers, orders, subscriptions and licences. Apps own their own subject matter and nothing else. An app never decides whether someone has paid — it asks, and caches the answer.

Licence authority · sells, renews, revokes Launch shop launchyourlife.co.za
verify · renew · revoke
Live Let's Connect connect.launchyourlife.co.za
Later App two <name>.launchyourlife.co.za
Later App three <name>.launchyourlife.co.za
Why this way round. A subscription changes state without anyone touching the app: it renews, it lapses, a card expires, someone cancels in month four. If each app holds its own copy of the truth, every one of those events has to be pushed to every app, and any app that misses a push is quietly wrong — still letting someone in, or locking out someone who paid.

The two ways to wire it

Pick one now
  Shop as authority Shop pushes to each app
Who knows if a subscription is live The shop. One answer. Every app holds a copy that can drift.
Adding app number four It calls one endpoint. Nothing in the shop changes. Shop learns a fourth API; four places to update on renewal.
A renewal fails in month six Shop marks it lapsed. Every app sees it on the next check. Shop must reach all four apps. A missed call means free access.
Customer buys two apps One account, two licences, one invoice. Two unrelated codes and no relationship between them.
Shop is down for an hour Apps run on cached entitlement. Needs designing. Apps unaffected — the one real advantage.
Work to build the first one More up front. Less up front, then compounding.
  Recommended Only if one app, forever
The outage risk is real and solvable. Verify when a code is first redeemed, then cache the entitlement locally with the date it was last confirmed. Re-check in the background, perhaps daily. If the shop cannot be reached, fail open for a grace period of a week or so. A couple sitting down on a Sunday evening should never be locked out of something they paid for because a server in Johannesburg is restarting.

The contract between them

Small on purpose

This is the entire coupling. Two endpoints and a shared secret — no shared code, no shared database, no shared repo.

// The shop, after a successful payment. Creates the licence and returns it.
POST launchyourlife.co.za/api/licences
     x-api-key: <per-app key>
     { product: "lets-connect", customer: {...}, plan: "monthly" }
  →  { key: "SXKS-6G2X-RMWT", expiresAt: "2026-09-16", status: "active" }

// The app, on redemption and then periodically. The only question it asks.
POST launchyourlife.co.za/api/licences/verify
     x-api-key: <per-app key>
     { product: "lets-connect", key: "SXKS-6G2X-RMWT" }
  →  { valid: true, expiresAt: "2026-09-16",
       holder: { partnerA: "Mark", partnerB: "Nikki" } }
Per-app keys, not one shared key. Each app gets its own, so a leaked key from a future app cannot mint licences for this one, and you can rotate one without touching the others. The comparison must be constant-time — Let's Connect already does this correctly with crypto.timingSafeEqual, and that code is worth copying forward.
The holder's names come back with the licence. That is what lets Let's Connect say "Welcome Mark and Nikki" without ever storing a customer record. The app stays account-free, which was the whole point of the redesign.

Repos and deploys

One per deployable

Plesk pulls one repository into one site. That is the unit, and it is why the answer is not "one project with two halves". Your ClaudeCode folder already holds eighteen projects this way.

RepositoryDeploys toOwns
Launch shop launchyourlife.co.za Customers, payments, subscriptions, licences, invoices
Let's Connect connect.launchyourlife.co.za Questions, decks, progress, its own admin
Each later app Its own subdomain Its own subject, and nothing about money
Never one repository for two sites. Both Plesk sites would pull the same commits, so a shop styling tweak drags a pull onto the app site too. Your own deploy notes record what that costs: a pull that includes a changed server.js without a restart leaves the old code running, and the document root silently reverted once and returned a 403 for the whole site. A Friday shop change should not be able to touch what two people are using that evening.
Shared context is a folder, not a repository. Keep them as siblings under ClaudeCode and open the parent folder when the work crosses both. I can read across both while git, Plesk and the deploy cycles stay completely separate. That gives you the shared understanding you want without the shared blast radius you do not.

How to get there from here

In this order
  1. 1

    Ship Let's Connect as it stands

    Perpetual codes, issued from its own admin. You can sell manually — generate a code, email it yourself — and take real money before any of this exists. Nothing below is required to make the first sale.

    Blocked only on a GitHub repo
  2. 2

    Add expiry to the licence

    An expires_at column and a check in the place that already re-reads the code on every request. Small, and it is the difference between a perpetual licence and a subscription. Null means perpetual, so every existing code keeps working.

    Do this before the shop, not after
  3. 3

    Build the shop against the contract

    Payment, orders, and the licence table. It calls the app's existing endpoint at first — no rewrite needed, because the endpoint already takes names and returns a code.

    The real build
  4. 4

    Invert, when app two is real

    Move the licence table to the shop and point the app's verification at it. Because the app already re-checks every request, this is a change to where the check reads from, not a change to when or whether it happens.

    Not before there is a second app
Phase two is the one people skip. Selling a subscription against a licence that cannot expire means every refund and every cancellation is a manual job you will do by hand, forever, and will eventually forget to do.

Decide before I build

Yours to call

Subscription or one-off?

You said subscription tokens, but the app sells a perpetual code. For a couples question deck, a one-off purchase is an easier sell and needs no expiry at all — people do not expect to rent a conversation.

My lean: one-off for this app, subscriptions for later tools. The platform should support both from day one.

Tokens as a wallet, or a licence per app?

"Subscription tokens for all of the apps" could mean a shared balance spent across apps, or simply one licence per app bought. These are very different builds — a wallet needs a ledger, balances and refund arithmetic.

My lean: a licence per app. Add a wallet only if you actually want cross-app bundles.

WooCommerce, or a custom shop?

WooCommerce gives you cart, VAT invoices, refunds, failed payments and PayFast integration off the shelf — and you already have a PayFast project. Custom means building all of that, none of which is your product.

My lean: WooCommerce plus a small plugin unless the storefront itself is the differentiator.

What does a lapsed subscription feel like?

When a subscription ends, does the deck stop dead, or go read-only, or keep the questions already seen? This is a product decision with real emotional weight — locking two people out mid-conversation is a bad memory of your brand.

My lean: finish the current session, then ask. Never interrupt a card.

Who sends the email?

Still unanswered from before, and it belongs to the shop now. The app returns a code once and never sees the customer again. The shop already owns the order confirmation.

My lean: the shop sends it, alongside the receipt.

What not to build yet

Deliberate
  • No shared login across apps. Let's Connect is deliberately account-free — two people, one screen, one code. Do not let a platform login creep in and undo that.
  • No shared component library. Two apps is not enough to know what is common. Copy the design system file into each; extract a library at four apps, if ever.
  • No single sign-on, no user profiles, no cross-app analytics. Each is a real project and none earns money until several apps exist.
  • No monorepo tooling. Nothing here needs a workspace manager. Two folders and two remotes is the whole system.
The pattern worth holding to. The shop is the only thing that knows about money. Every app knows only its own subject and one question it can ask. Keep that line clean and adding the fifth app stays a weekend; blur it and each new app inherits the last one's billing bugs.
Written against Let's Connect v1.11.1. Verified in code: no licence expiry exists; the couple's licence is re-read on every request at server.js:567; codes are issued via POST /api/shop/codes guarded by a constant-time key comparison.
